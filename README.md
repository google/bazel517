# `bazel517`

`bazel517` is a Python build backend (PEP 517 / PEP 660) for projects that already build their wheels with Bazel (for example via `rules_python`'s `py_wheel` rule). Point it at your Bazel wheel target in `pyproject.toml`, and standard Python packaging frontends like `pip install .`, `pip install -e .`, `uv pip install .`, and `python -m build` will invoke Bazel to build the wheel.

## Usage

Configure `bazel517` as your build backend and specify the Bazel wheel target in `[tool.bazel517]`:

```toml
[build-system]
requires = ["bazel517"]
build-backend = "bazel517"

[project]
name = "torch_tpu"
dynamic = ["version"]
requires-python = ">=3.11"

[tool.bazel517]
target = "//ci/wheel:torch_tpu_wheel"
bazel-args = [
    "-c", "opt",
    "--config=wheel_common",
    "--repo_env=HERMETIC_PYTHON_VERSION={python_version}",
    "--define=PYTHON_VERSION={python_version_abi}",
    "--@rules_python//python/config_settings:py_freethreaded={freethreaded}",
]
```

Because the wheel metadata is already generated by the Bazel `py_wheel` target, `build_wheel` and `build_editable` don't require a static `version` in `[project]`. You only need static `[project]` metadata if you want to build source distributions with `build_sdist`.

### Template placeholders

Strings in `bazel-args`, `editable-bazel-args`, and `[tool.bazel517.env]` are interpolated against the active Python interpreter running the build hook:

- `{python_version}`: `"3.13"`, `"3.14"`, etc.
- `{python_version_nodot}`: `"313"`, `"314"`, etc.
- `{python_version_abi}`: `"3.13"`, or `"3.14t"` on a free-threaded interpreter
- `{python_abi_tag}`: `"cp313"`, `"cp314t"`, etc.
- `{freethreaded}`: `"yes"` if `Py_GIL_DISABLED` is set, otherwise `"no"`
- `{python_executable}`: `sys.executable`

If you need different flags for editable installs than for release wheels, you can set `editable-bazel-args` in `[tool.bazel517]`; otherwise it defaults to `bazel-args`.

### Passing extra Bazel flags at build time

Additional Bazel flags can be appended at invocation time via PEP 517 `--config-settings` (`-C`) or the `BAZEL517_BAZEL_ARGS` environment variable:

```bash
pip install . -C bazel-args="--config=local_torch" -C bazel-args="--config=no_rbe"
uv pip install -e . -C bazel-args="--config=local_torch"
BAZEL517_BAZEL_ARGS="--config=no_rbe" pip install .
```

## How it works

When resolving the Bazel executable, `bazel517` uses an explicit `bazel-bin` setting (from `-C bazel-bin=...`, `BAZEL_BIN`, or `[tool.bazel517].bazel-bin`) if one is provided. Otherwise it looks for `bazelisk` and then `bazel` on `PATH`, and if neither is installed it downloads and caches a `bazelisk` binary (verified by SHA-256) in `~/.cache/bazel517`.

For a standard wheel build (`build_wheel`), `bazel517` runs `bazel build` on the configured target with `--build_event_json_file`, reads the resulting `.whl` path from the Build Event Protocol output, and copies the wheel into the directory requested by the frontend.

For an editable install (`build_editable`), `bazel517` builds the wheel target and then runs `bazel aquery` against the `PyWheel` action (using the canonicalized flags from the build event stream) to inspect the `--strip_path_prefix` and `--input_file_list` arguments passed to `rules_python`'s wheelmaker. From those inputs, it determines which files in the wheel came from workspace `.py` / `.pyi` sources rather than generated or compiled outputs in `bazel-out/`. It strips the workspace Python sources from the wheel while leaving compiled extensions (such as `.so` files) and generated modules intact, and adds a `.pth` file and `MetaPathFinder` hook that merges the workspace source directories with the installed `site-packages` package directories on `__path__`.
